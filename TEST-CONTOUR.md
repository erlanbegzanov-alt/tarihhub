# Тестовый контур

Два сайта из одного репозитория. Боевой — тот, которым пользуются школьники.
Тестовый — тот, который можно ломать.

|                  | Боевой                     | Тестовый                          |
| ---------------- | -------------------------- | --------------------------------- |
| Ветка            | `master`                   | `test`                            |
| Адрес            | боевой домен Vercel        | preview-адрес ветки `test`        |
| База Firestore   | `tarihhub-a6748`           | отдельный проект                  |
| `VITE_APP_ENV`   | `production`               | `test`                            |
| Метка в углу     | нет                        | золотая «ТЕСТ» + имя базы         |
| Дев-панель XP    | вырезана из сборки         | есть                              |
| Новые фичи       | по флагу                   | все включены                      |

Код один и тот же. Разделяют их только переменные сборки — все решения о том,
что значит «тест», собраны в одном файле: `src/lib/environment.ts`.

Главное, что даёт разделение баз: батл на тестовом сайте не может испортить
рейтинг, XP и таблицу лидеров реальных детей. Пока база одна, любая тестовая
игра — это запись в те же документы, которые читает боевой сайт.

---

## Что уже сделано

- ветка `test` заведена от текущей работы (это `master` + три твоих
  невыложенных фикса урока и чата);
- `src/lib/environment.ts` — единственное место, где решается, что такое тест;
- `src/components/TestModeBadge.tsx` — золотая метка в правом нижнем углу,
  показывает, **к какой базе подключён сайт**. Если на тестовом сайте видно
  `tarihhub-a6748` — значит тест смотрит в боевую базу, и работать нельзя;
- дев-панель на `/profile` теперь живёт и на тестовом сайте (боевая сборка её
  по-прежнему физически не содержит);
- флаг `VITE_FEATURE_TEAM_BATTLE` — командный батл можно мержить в `master`
  частями, пока он невидим пользователям.

## Что нужно сделать руками — четыре шага

Это те шаги, которые может сделать только владелец аккаунтов.

### 1. Отдельный проект Firebase

[console.firebase.google.com](https://console.firebase.google.com/) → Add
project → имя вроде `tarihhub-test`. План Spark, карта не нужна. Дальше внутри
проекта:

- **Firestore Database** → Create database → регион `eur3` (тот же, что у
  боевого, чтобы задержки были похожи);
- **Authentication** → Sign-in method → включить **Google**;
- **Project settings** → Your apps → Web app (`</>`) → зарегистрировать →
  скопировать шесть значений из блока `firebaseConfig`.

Шесть значений никуда не вставляй в переписку — они идут прямо в Vercel.

### 2. Переменные Preview в Vercel

Vercel → проект `tarihhub` → Settings → Environment Variables. Для каждой
переменной выбирай окружение **Preview** (не Production):

```
VITE_FIREBASE_API_KEY              → из тестового проекта
VITE_FIREBASE_AUTH_DOMAIN          → <тест-проект>.firebaseapp.com
VITE_FIREBASE_PROJECT_ID           → <тест-проект>
VITE_FIREBASE_STORAGE_BUCKET       → из тестового проекта
VITE_FIREBASE_MESSAGING_SENDER_ID  → из тестового проекта
VITE_FIREBASE_APP_ID               → из тестового проекта
VITE_APP_ENV                       → test
```

И одну для **Production**, если её там ещё нет:

```
VITE_APP_ENV                       → production
```

Без неё боевой сайт всё равно ведёт себя как боевой, но тестовый код остаётся
в бандле мёртвым грузом вместо того, чтобы быть вырезанным.

### 3. Разрешить тестовый вход в CSP

Заголовок Content-Security-Policy запрещает странице открывать окна чужих
доменов. Вход через Google открывает окно `<проект>.firebaseapp.com` — сейчас
там прописан только боевой проект, поэтому на тестовом сайте вход молча не
сработает.

В `vercel.json` найди эту строку — она встречается ровно один раз:

```
frame-src https://tarihhub-a6748.firebaseapp.com
```

и допиши тестовый домен через пробел:

```
frame-src https://tarihhub-a6748.firebaseapp.com https://<тест-проект>.firebaseapp.com
```

Ничего больше в этой строке не меняй. `connect-src` трогать не нужно — там
уже `https://*.googleapis.com`, он покрывает любой проект.

### 4. Разрешить адрес тестового сайта в Firebase

После первого деплоя ветки `test` Vercel покажет два адреса: постоянный адрес
ветки (в нём есть `-git-test-`) и адрес конкретного деплоя (со случайным
набором букв). **Нужен первый.** Второй меняется при каждом коммите, и вход
будет отваливаться после каждого деплоя.

Firebase (тестовый проект) → Authentication → Settings → Authorized domains →
Add domain → вставить постоянный адрес ветки без `https://`.

### Правила Firestore

Правила лежат в git одним файлом `firestore.rules`, но выкатываются в каждый
проект отдельной командой. Для тестового:

```bash
npx firebase login
npx firebase deploy --only firestore:rules --project <тест-проект>
```

Перед выкаткой правил стоит прогнать их тесты — они уже есть в проекте и
работают на эмуляторе, никакую живую базу не трогают:

```bash
npm run test:rules
```

## Как работать дальше

```bash
git checkout test
# правки
git push            # Vercel сам пересоберёт тестовый адрес
```

Локально тестовый контур поднимается тем же `.env.local`: подставь в него
шесть ключей тестового проекта и `VITE_APP_ENV=test`. Метка «ТЕСТ» в углу —
проверка, что всё сошлось.

## Как выкатить в прод, чтобы никто не заметил

Смысл флага в том, что код едет в прод заранее и молчит. Не нужно копить
месяц изменений в ветке, а потом одним махом вливать — это и есть главный
источник «выкатили и всё легло».

1. **Слить код.** `test` → `master`, обычным PR. Флаг выключен, на боевом
   сайте ничего не меняется — фичи там просто нет в бандле.
2. **Выкатить правила на боевой проект.** Строго до включения флага:

   ```bash
   npm run test:rules
   npx firebase deploy --only firestore:rules --project tarihhub-a6748
   ```

   Если сделать наоборот, фича появится, а каждая запись будет отбиваться
   правилами — и выглядеть это будет как сломанный сайт.
3. **Включить флаг.** Vercel → Environment Variables → Production →
   `VITE_FEATURE_TEAM_BATTLE=1` → Redeploy. Фича появляется без единого
   коммита.
4. **Если что-то не так** — убрать переменную и передеплоить. Откат занимает
   минуту и не требует revert'а в git.

## Что тестовый контур НЕ изолирует

Честный список, чтобы не было сюрпризов:

- **Cloudinary** — аккаунт один. Картинки, загруженные в Кахут на тесте,
  лягут в ту же медиатеку, что и боевые.
- **Gemini** — ключ задан только для Production. На тестовом сайте AI-чат
  будет отвечать заготовленными ответами, а не живой моделью. Если добавить
  ключ и в Preview — квота будет общей с боевым сайтом.
- **Тестовый сайт закрыт входом в Vercel.** На проекте включена Deployment
  Protection: открыть адрес может только тот, кто вошёл в Vercel с доступом к
  проекту. Для тебя это удобно, но команда без аккаунта его не откроет. Если
  нужно дать доступ тестерам — Vercel → Settings → Deployment Protection. Не
  выключай защиту совсем, пока тест не подключён к своей базе.
- **PWA.** Если установить тестовый сайт на телефон, появится вторая иконка с
  тем же названием. Метка «ТЕСТ» видна и внутри установленного приложения —
  ориентируйся на неё.
- **Правила Firestore** выкатываются в два проекта двумя командами. Забыть
  боевой — самая вероятная ошибка в этом списке.
